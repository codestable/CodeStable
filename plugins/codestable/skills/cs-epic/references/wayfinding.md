# Epic 路线发现

只在大需求已经归属 `cs-epic`，但仍无法写成可审查的 proposed Epic 时使用。它负责把路线级迷雾
收敛成执行契约，不负责实现目的地。普通功能、路线已经清晰的 Epic、单个局部技术未知，以及仅因
高风险、文件多或跨会话产生的连续性需要，都不触发本方法。

## 触发与归属

完成一次有界仓库调查和当前最多 3 个方向性澄清问题后，同时满足以下条件才进入路线发现：

- 工作确实大到需要 Epic；
- 多个相互依赖的产品或路线级决策阻止形成目标、边界、验收或子项契约；
- 这些问题预计无法在当前会话内自然收敛。

永久 Epic 文档就是唯一路线文档，proposed 阶段的相关小节共同组成低分辨率文档内路线地图。
路线发现不创建独立 issue、map 或第三套状态，也不新增独立路线文件。work 游标只保存永久文档指针、
当前 frontier 决策名称、下一步、阻塞与证据指针，不复制问题、依赖图、答案、验收或子项定义。
路线地图是索引，不是存储区；已有 research、prototype、ADR 或项目文档拥有细节时，Epic 只记录结论
影响与指针。

## 文档内路线地图

地图由同一永久 Epic 中的四个互斥区域组成：目标、范围、非目标与验收描述目的地，其中 `非目标`
记录已判定的范围之外；`待决策` 保存
现在能精确陈述的问题；`尚未明确` 保存仍不能精确陈述的迷雾；`关键决策` 保存已解决结论与证据
指针。同一事项只能位于 `待决策`、`尚未明确`、`关键决策` 或 `非目标` 之一，移动时删除旧表示。
术语歧义沿用同一地图：不能精确区分概念时属于 `尚未明确`；能问清事实或产品含义时成为 AFK/HITL
决策，不新增术语状态。详细收敛规则见 `shared-language.md`。

每个待决策节点必须标为 `AFK` 或 `HITL`，并使用以下最小格式；人类可见处始终连同可读名称引用，
不得只写裸 `DEC-*`：

```markdown
- **DEC-1 · {可读名称}** `[AFK|HITL]`
  - question: {一个精确问题}
  - depends_on: [{完整决策名称} | none]
  - method: research | owner-dialogue | prototype | prerequisite
  - evidence: {pointer | pending}
```

frontier 只派生、不持久化：它是 `待决策` 中所有 `depends_on` 已进入 `关键决策` 的节点。依赖被
移入 `非目标` 或删除时，在同次更新中移除相应依赖边，再重新派生 frontier。被阻塞但已经能精确
陈述的问题仍留在 `待决策`，不能退回迷雾；`尚未明确` 不分配 DEC 名称、依赖或解决者。
未指定下一步时按永久文档顺序选择第一个 frontier 节点，work 的 `next_action` 只指向其完整名称，
不复制 frontier 清单或依赖图。

## AFK 与 Human In The Loop

- **AFK**：仓库事实、外部资料以及能由已批准约束唯一推出的工程判断由 agent 自行解决。独立的
  AFK frontier 节点可以并行调查，但主流程是永久 Epic 路线地图的唯一写者。
- **HITL**：产品结果、范围与非目标、验收口径、用户偏好、需要外部权限的动作，以及存在真实取舍
  的路线选择必须由 owner 决定。agent 先给出已知事实、候选项与取舍、推荐及依据，以及不同选择
  如何改变路线；不得替 owner 回答 HITL 问题，不得把沉默当作选择。
- 一次只向 owner 提交一个 HITL frontier 节点，因为它必须先备齐事实、选项、取舍、建议与路线影响；
  记录答案并更新地图后再选择下一个。handoff 或永久
  文档已经确认的选择不重复询问，仓库可核实的事实不交给 owner。
- 用于判断“应该长什么样或怎样表现”的 prototype，其制作可以由 agent 完成，但取舍结论在 owner
  看过具体 artifact 并回答具体问题前仍是 HITL。prototype 只能是可丢弃探索产物，不得把探索代码
  留在产品工作树或里程碑；探索产物不自动晋升为交付。批准后确需复用时，owning skill 把它作为
  未验证输入重新纳入实现，并完整通过该 skill 选定的保障与验证，禁止直接搬入里程碑。
- prerequisite 只用于解除某个决策的真实阻塞，不得借路线发现交付目的地，也不得在产品工作树
  留下未批准改动或进入里程碑。涉及外部权限、代码外副作用或不可逆动作的 prerequisite 一律标为
  `HITL`，执行动作前仍须另获对应权限或确认；HITL 回答本身不构成授权。HITL 是规划交互，不是新的
  owner gate，也不代表 Epic、commit、执行或发布已经获批。

## 找路

1. **目的地先于路线。** 按当前证据写出足以界定探索范围的目标、范围、非目标与验收草案；它们
   可以在 proposed 阶段随决策收敛，完整冻结是 route clear 的条件。目的地仍无法命名时先解决它，
   不预拆执行项。
2. **广度优先绘图。** 横向找出现在已能精确陈述、且会改变执行路线的问题写入 `待决策`，补齐
   `AFK|HITL`、依赖、方式与证据。仍知道其相关但暂时无法精确陈述的区域写入 `尚未明确`；能否
   精确提问决定它是节点还是迷雾，不由能否立即回答、是否被阻塞决定。
3. **推进 frontier。** AFK 节点由 agent 调查；HITL 节点按上节交给 owner。每解决一个节点，在同次
   更新中从 `待决策` 移除、以同一完整名称写入 `关键决策`、更新受影响依赖，并重看 `尚未明确`：
   现在可精确提问的内容提升为新节点，超出目的地的内容移入 `非目标`，已失效的问题删除。最后
   重新计算 frontier，并让 work 的 `next_action` 指向下一个节点。AFK 结论在批准前被新证据推翻时，
   从 `关键决策` 移回 `待决策` 或 `尚未明确`，使依赖它的节点重新阻塞后再计算 frontier。
4. **处理断路。** `待决策` 非空但 frontier 为空时，先检查缺失依赖或依赖环；真实外部阻塞才写入
   work 的 `blocked_by`。依赖环必须通过拆分、合并或重述节点消除，不能当成外部阻塞。只有迷雾而
   没有 frontier 时继续定向调查以展开迷雾，不能宣称 route clear。AFK research 的低价值中间材料
   直接丢弃；稳定结论和最小证据摘要进入 `关键决策`，确需保留细节时沿用项目 canonical 文档并留指针，
   不为它新增路线文件。
5. **形成交付路线。** 决策问题解决的是“怎么走”，Epic 子项交付的是可验收结果；不把决策问题
   一对一变成 Epic 子项。只有路线足够稳定后，才写带稳定 ID、owning skill、依赖、验收要点和必要
   设计约束的子项契约。

## Route Clear

路线清晰、可审查、可执行，必须同时满足：

- 目标、范围、非目标和整体验收可以冻结；
- route clear 前不得保留 `HITL` 节点；所有仍有效的 HITL 节点已经由 owner 明确解决，或经 owner
  明确确认后移入 `非目标`；只有因已确认上游决策而机械失效的节点可带依据删除；agent 不得单方
  判定 HITL 节点超出范围或失效；
- 没有仍会改变目标、范围、非目标、验收、子项边界、依赖或重大风险的 `待决策`；
- `尚未明确` 为空；只有 `AFK` 的局部未知可以下放给某个子项的 owning skill，且不能再改变
  目标、范围、非目标、验收、子项边界、依赖或重大风险；
- 会改变路线的术语已经单义化、定义或链接，概念关系经具体场景检验，全部子项使用同一词汇；
- 每个子项都是可交付切片，并写明稳定 ID、owning skill、依赖、验收要点与必要设计约束；
- 一个不了解探索过程的执行 agent，只读完整 proposed Epic 就能判断先做什么、完成标准是什么，
  以及何时必须回到 Epic 重新确认契约。

route clear 不是“所有实现细节都已决定”，也不是新的 owner gate、执行授权、commit 授权或发布授权。
达到它之后才冻结完整 proposed Epic，进入现有 design review；review findings 收敛后仍由 owner 执行
现有第一道确认。冻结前移除 `待决策` 与 `尚未明确` 两节；只有 `AFK` 的局部未知可以下放并归入
对应子项契约，仅把已解决决策和下放 AFK 局部未知带来的剩余风险归入 `遗留风险`。批准 revision
生效后，路线发现结束，`cs-epic` 的执行循环接管。
