# 代码与模块设计

好的结构，是让调用方用更少的认知换到更多的能力。设计模块时核心方向只有一个：往深里做。（源自 codestable-lite 分支的实践沉淀）

## 词汇

- **模块**：任何"有接口、有实现"的东西——函数、类、包、跨层切片都算。
- **接口**：调用方为正确使用必须知道的全部信息——不只类型签名，还有不变量、调用顺序、错误模式、性能特征。
- **深度**：接口的杠杆。小接口藏大行为是深；接口和实现差不多复杂是浅。深是接口的属性，不是实现的属性。
- **接缝**：可以改变行为、但不必在当前位置改代码的地方。

## 先定归属和名字

设计新能力时，先问它**属于哪里**、沿用现有词汇**叫什么**，再问接口怎么做深。

默认的失败方式：图方便把能力丢进最近的文件，顺手起一个新同义词——长出平行实现、劈开命名空间、搜索从此失效。先搜现有概念与同义词：能扩展本该拥有它的模块就扩展；确实没有归属才新开模块。**归属仍对 → 扩展做深；业务形状已变 → 先重切再改行为。**

## 结构跟着业务形状走

出现任一信号，先做服务于当前目标的结构调整，再实施行为变更：

- **新变化轴**：引入的是独立规则、策略、阶段或生命周期，不是旧分支的参数微调；
- **容器对不上**：现有文件/函数/模块的名字与职责说不清新逻辑该放哪；
- **改一处牵一片**：同一规则要在多处复制，或改完难解释、难验证。

**先改善可修改性，再实施行为变更。** 结构调整必须被当前目标约束——判断标准是"调整后这次修改更局部、更可解释、更容易验证"，没有行数/文件数配额；只是顺手整理或为想象中的未来造接缝的，不做。

## 往深里做

- 接口反复问三件事：能不能少几个方法？能不能简化参数？能不能把更多复杂度藏进去？
- **删除测试**：假想删掉这个模块——复杂度跟着消失，它只是穿透层；复杂度会在多个调用方重新冒出来，它才值得存在。
- 深模块内部可以有小部件和内部接缝；只要不泄漏到对外接口，就不增加调用方负担。

## 接缝必须真实

不为"看起来可扩展"提前造接缝。**一个 adapter 只是想象中的接缝，两个 adapter 才说明这里真有变化维度。** 真实接缝至少满足一种：生产与测试需要不同实现；多运行环境需要不同实现；依赖不可控必须隔离。选了有已知上限的简单实现时，按 economy.md 记录有界简化，真实变化出现后再放接缝。

## 接口就是测试面

- 调用方和测试穿过**同一道接口**；测试总想钻到接口背后，通常说明模块形状不对。
- 依赖靠注入、返回结果少造隐式副作用、表面积小。
- **替换，别叠加**：模块做深后，围着旧浅模块写的单测通常该删；在新接口上重写，断言可观察结果而不是内部状态。

## 把边界收进设计

深模块替调用方吃掉常见边界：必填/格式/范围/幂等/权限/依赖失败的校验要有归属层，不散落各处各写一遍；错误信息指向可修复动作；删除/覆盖/发布/扣费等危险操作要有确认、防重复与可恢复路径。每个调用方都要自己记一套边界清单，说明模块还不够深。

## 重要接口设计两遍

第一个冒出来的接口通常只是最顺手的版本。重要接口从几个方向各设计一版（最小表面积 / 为常见调用方优化 / 保留必要灵活性），按深度、改动集中度、接缝真实性比较后选。

## 穿刺：高风险先通再铺

存在会卡死方案的技术/集成风险时，不要先铺完整实现：

1. **锁定风险表**：一句话说清做完后的可观察结果；列 2–5 个会卡死或大改方案的风险点（主路径端到端、鉴权、数据形状、外部依赖、迁移兼容、失败恢复），每点写清**怎样算打通**。
2. **按"不确定 × 失败代价"降序**，先做最可能推翻方案的点。
3. **逐点最小打通**：接到真实归属；一点不通就停，先处理方案或问用户。**mock 只挡不可控外部，不 mock 掉本次要证明的那一环。**
4. **主路径端到端**跑通一次（能演示或脚本验证）后再加厚；未通之前不做样式打磨、次要入口、大范围重构。

打通的代码默认是正式骨架，不是可扔的 spike。
