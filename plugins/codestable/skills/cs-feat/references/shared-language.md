# Feature 共享语言

只在新词、重载词或相邻概念边界会改变功能行为、归属、公开契约或验收时使用。普通改动沿用已有
单义词汇时跳过，不把每个 Feature 变成领域建模阶段。

## 收敛局部语义

1. 先搜索项目已有 glossary、domain 文档、需求、ADR、相邻代码、API、schema 与测试。已有
   canonical 定义优先；用户表达与它冲突时立即指出，不静默另造同义词。
2. 区分两类词。领域术语定义业务概念本身，不混入存储或框架细节；架构角色只说明本设计中的
   责任、权威来源和排除边界，不冒充长期领域词汇。
3. 仓库与文档可唯一核实的事实由 agent 解决；产品含义、命名偏好或真实概念边界需要 owner 选择。
   不把可调查事实上交，也不替 owner 决定业务语义。
4. 最小术语契约只写 canonical 名称、紧凑定义、排除含义和一个边界场景。关系比词典更重要时，
   补一条相邻概念关系或不变量；不为每个实现名词建立条目。
5. 用具体输入、事件或失败场景检查定义。场景必须能区分相邻概念，并给出可观察结果；若结果仍有
   两种合理解释，语义尚未清晰，回到事实调查或 owner 选择。

## 完成与归属

局部共享语言清晰的判据是：每个会改变行为或验收的术语只有一个含义，且实现、API、schema、文档与
测试使用同一含义；一个不了解讨论过程的实现者能从定义和边界场景判断预期行为。

已有项目领域文档拥有跨任务稳定术语；当前设计只链接，不复制。没有 canonical 归宿时，先把本次
定义留在已有 design 或 task packet；当前会话内完成且两者都不存在时写入现有交付摘要，不为术语新建
专用产物；跨会话且前述载体不存在时写入既有 work 游标的 `边界` 节，不为术语新建 work。跨任务稳定
后给出建议落点，owner 可在既有 gate 或后续治理中选择；未选择归宿不阻塞当前交付，也不自动创建
`CONTEXT.md`、glossary 或平行真相。架构角色留在当前设计；只有难回退、缺少上下文会意外且来自真实
取舍的决定才进入 ADR。

这不是新的 gate。事实能唯一确定时直接继续；只有真实产品语义选择才使用既有 owner 确认。
