# 实现经济性

经济性不是把代码写短，而是在理解真实路径与质量承诺之后，用系统能长期承受的**最少新增复杂度**完成变化。它同时防两端：过度工程与草率最小化。（源自 codestable-lite 分支的实践沉淀）

## 先理解，再最小化

最小化只能在现状模型成立后使用：先顺清触发、责任、数据、状态、调用方和可观察结果，再判断哪一层能力足够。没有理解路径时，"最小 diff"往往只是改在最近的位置，而不是正确的位置。

## 从不新增开始（五级梯子，命中即停）

1. 目标是否已由现有行为满足，或能靠删除、收窄需求、调配置、修规格完成——不新增行为；
2. 正确归属的现有模块 / helper / 规则是否已提供能力——先搜索复用，不建平行实现；
3. 标准库、语言机制、平台原生能力（浏览器 / OS / 数据库）是否完整覆盖；
4. 已安装依赖是否已提供——不为几行稳定代码加新依赖，也不在现成依赖旁手写第二套；
5. 都不成立，才写完成当前目标所需的最小新代码。

## 在正确责任边界修一次

**最小充分 ≠ 最小 diff，也不是保留当前文件形状。** bug 报告通常只给一条症状路径；改共享责任前先搜调用方与相邻入口，确认无效状态最早在哪产生——能在共同归属处消除根因，就不在每个调用方各加一个 guard。在错误容器里多加一个分支，常比抽一个深模块更贵。必要的结构调整（抽取/合并/下沉）可以先做，前提是直接降低当前变化的风险或认知负荷。

## 不为想象中的未来付费

没有真实变化维度时，不加只有一个实现的接口、只有一个产品的工厂、没人会改的配置、只转发调用的 wrapper。新抽象、新接缝、新依赖都要能指出**当前**调用方、**当前**差异或**当前**风险。这不是禁止扩展性——已确认的兼容策略、部署差异、测试替身就是今天的证据。

## 有界简化（三要素齐才算数）

当前最合适的方案有已知上限时（线性扫描只适合当前数据量、全局锁只适合当前吞吐），采用它并紧凑记录：

- **已知上限**：什么规模、环境或输入下开始失效；
- **升级触发**：出现什么可观察证据时需要重新设计；
- **升级方向**：届时替换哪一层能力（不是今天提前实现）。

**没有上限或触发条件的"先这样"不是有界简化。** 升级触发已发生却仍破坏目标的，不能包装成可交付的简化。记录落点：影响本次交付的写进 work 文档；长期有效的坑点沉淀为 lesson。

## 保护不能被省略的部分

最小化不删除：用户明确要求与既有约束；信任边界的输入校验、权限与信息安全控制；防数据丢失或不可逆副作用的错误处理；可访问性基础与危险操作护栏；与失败代价相称的验证证据。这些不是"额外保险"，是完整解的一部分。

## 留下最小有用反馈

非平凡逻辑变化至少留一个可运行、会在该行为再次损坏时失败的检查；优先复用现有测试入口，不新建测试框架。涉及解析、分支、金额、权限、迁移或数据丢失风险时，不能以"改动很小"省略反馈回路。同一行为复制到生成文件或多副本时，人工提醒不是反馈回路——建单一来源加一致性检查。

## 对收益保持诚实

可以汇报删除了什么、避免新增了什么、何时需要升级；**没有真实对照基线时，不声称"节省了多少行、多少成本"**。最小实现的价值由更小的责任面和可验证结果支撑，不靠虚构数字。
