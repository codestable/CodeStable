# 原则：代码与模块设计

好的结构，是让调用方用更少的认知，换到更多的能力。设计模块时，核心方向只有一个：往深里做。

## 背景

代码通常不是一下子坏掉的，而是在演化里慢慢变浅、变散。

一种坏法是模块太**浅**：接口几乎和实现一样复杂，调用方要理解的东西和自己重写一遍差不多，这层封装没有省下认知。另一种坏法是概念太**散**：同一个能力散在十几个小模块里，读懂一件事要在文件之间来回跳。浅和散都会增加认知负荷，也会让代码难测、难改，AI 也更难导航。

CodeStable 里没有单独的“重构”流水线。模块的抽取、合并、下沉，应该长在实现 feature 的过程中。但顺手改也需要一把尺子，否则很容易把代码改得更碎。这把尺子就是**深度**：用尽量小、稳定、好理解的接口，承载尽量多的行为。

## 原则

### 先把词定准

这套判断依赖几个稳定的词。不要随手换成"组件"、"服务"、"API"、"边界"这类更含糊的说法。

- **模块（module）**：任何"有接口、有实现"的东西。规模不限，一个函数、一个类、一个包、一段跨层切片，都可以是模块。
- **接口（interface）**：调用方为了正确使用模块必须知道的全部信息。它不只是类型签名，还包括不变量、调用顺序、错误模式、必要配置和性能特征。
- **深度（depth）**：接口的杠杆。调用方每学一点接口，能换回多少行为。小接口后面藏了大量行为，就是深；接口和实现差不多复杂，就是浅。
- **接缝（seam）**：可以改变行为、但不必在当前位置改代码的地方。接缝通常就是接口所在的位置；接缝放哪，和接缝后面放什么，是两个不同的设计决定。

### 先定归属和名字

设计新能力时，先问它**属于哪里**、应该沿用现有词汇**叫什么**，再问接口怎么做深。

默认的失败方式，是图方便把能力丢进最近的文件，顺手起一个新同义词。这样会长出平行实现，把命名空间劈成两半，搜索也从此失效。先搜一遍现有概念和同义词：能扩展那个本该拥有它的模块，就扩展；确实没有合适归属，再新开一个模块。

**归属仍对 → 扩展做深；业务形状已变 → 先重切再改行为。** 扩展不是默认正确，只是「容器与概念仍匹配」时的默认。

### 结构跟着业务形状走

业务概念、变化轴或生命周期已经变了，代码的归属与边界也要跟着重切。在旧容器上继续堆分支，常常不是更省，而是把系统总复杂度抬高。

默认的失败方式，是业务逻辑已经需要独立模块，却仍在原文件的 if-else / 大函数里硬塞新分支；或把新规则塞进名字与职责已经说不清的落点。

出现下面任一信号，应先做服务于当前目标的结构调整，再实施行为变更：

- **新变化轴**：这次引入的不是旧分支上的参数微调，而是独立规则、策略、阶段或生命周期。
- **容器对不上**：现有文件 / 函数 / 模块的名字与职责，已经说不清新逻辑该放哪。
- **改一处牵一片**：同一规则要在多处复制，或改完难解释、难验证。

典型做法：从旧 if-else 或过大模块里**抽出**与新业务轴对应的部分，落到正确归属，再在新边界上改行为。不是为「看起来干净」而搬家。

**先改善可修改性，再实施行为变更。** 不要把新行为硬塞进错误归属、重复概念或过浅接口。可以做的结构步包括：明确能力归属、统一命名、收拢重复规则、抽取/合并/下沉模块、压缩接口表面积、建立必要的验证入口。然后再改行为。

结构调整必须有当前目标约束，不能借机做无关重构。判断标准只有业务与风险，**没有「允许多大抽取」的行数/文件数配额**：

- 做：调整后，这次目标修改更局部、更可解释、更容易验证。
- 不做：不能降低这次变更的风险或认知负荷；只是顺手整理、重命名或为想象中的未来造接缝。

范围或风险因此失控时，升管理强度（见 `SKILL.md` 与 [fast](fast.md) 反射信号），而不是用 diff 大小禁止该做的结构步。
### 往深里做

- 设计接口时反复问三件事：**能不能少几个方法？能不能简化参数？能不能把更多复杂度藏进去？**
- 做一次**删除测试**：假想把这个模块删掉。如果复杂度也跟着消失，它只是穿透层，白占一层；如果复杂度会在多个调用方重新冒出来，它就在替系统省认知，值得存在。
- 记住：**深是接口的属性，不是实现的属性。** 深模块内部仍然可以由小部件组成，也可以有内部接缝。只要这些内部结构不泄漏到对外接口上，它们就不会增加调用方的认知负担。

### 接缝必须真实

不要为了"看起来可扩展"提前造接缝。一个 adapter 只是想象中的接缝，两个 adapter 才说明这里真的有变化维度。

通常，真实接缝至少要满足一种情况：生产和测试需要不同实现；多个运行环境需要不同实现；依赖本身不可控，必须隔离在可替换的位置。否则，只有单个实现的接缝往往只是多绕了一层。

如果当前选择一个更简单但有已知容量、环境或算法上限的实现，不要为了消除心理负担就提前造接缝。按 `economy.md` 记录上限、升级触发和届时应替换的能力层；真实变化出现以后，再把接缝放到那个会变化的位置。

### 接口就是测试面

- 调用方和测试应该穿过**同一道接口**。如果测试总想钻到接口背后，通常说明模块形状还不对。
- 让接口天然好测：依赖靠注入，不在内部自己 new；返回结果，少制造隐式副作用；表面积要小，方法和参数越少，测试搭建越轻。
- 接缝后面怎么测，取决于依赖性质。纯计算就通过新接口直接测；自己的远程服务可以定义 port，生产用真实 adapter，测试用内存 adapter；不可控第三方，比如支付、短信，就把它当注入的 port，测试时给 mock。
- **替换，别叠加。** 模块做深后，原先围着浅模块写的单测通常该删掉。在新接口上重写测试，断言可观察结果，而不是内部状态。这样的测试能扛住内部重构，只在行为真的变了时才需要改。

### 把边界和易用性收进设计

设计不是只让 happy path 能跑。一个深模块应该替调用方吃掉常见边界，让使用者不必在每个入口重复猜“这里要不要判空、禁用、确认、加载中”。

- 输入边界要有归属：必填、格式、范围、重复提交、幂等、权限、资源不存在、外部依赖失败，都要决定在哪一层校验和报错。不要让同一条规则散落在前端、API、数据库和测试里各写一遍。
- 默认路径要省心：常见参数给默认值，罕见配置藏到可选入口；错误信息要指向可修复动作，不要把内部异常直接甩给调用方或用户。
- 前端状态也是接口契约：加载中、空状态、错误状态、禁用状态、重复点击、请求取消、乐观更新失败，都应该在组件或交互模型里有明确设计，而不是等用户点出问题再补。
- 危险操作必须有护栏：删除、覆盖、重置、发布、扣费、权限变更等动作，要有二次确认、不可逆提示、执行中防重复提交，以及失败后的可恢复路径。
- 边界处理要提升深度，不要污染接口。优先把校验、状态机和确认流程封进合适模块；如果每个调用方都要自己记一套边界清单，说明模块还不够深。

### 按质量目标看设计

`quality.md` 负责选择和定义当前 issue 的质量目标；这里负责把已选目标落实成模块与接口判断。不要重新发明“可测试性、可观测性、易用性”并列的第二套质量分类。

- 功能适宜性与交互能力通常影响能力归属、默认路径、用户状态、错误提示和防误用设计。
- 性能效率影响工作量归属、批处理、缓存、资源上限、背压和容量边界。
- 兼容性与灵活性影响共享契约、版本策略、迁移路径、环境差异和可替换接缝。
- 可靠性、信息安全性与安全性分别要求明确失败恢复、攻击防护和危害控制由哪一层负责，不能把三者混成一个“安全”标签。
- 可维护性要求能力归属、命名、规则集中度、可分析性和测试面保持清楚。

测试接口、依赖注入、日志、指标和状态暴露是常见工程手段。把它们写在所支撑的质量目标下面，并说明为什么该手段能产生目标需要的证据。没有被选中的特性不需要补一段设计说明。

### 重要接口要设计两遍

第一个冒出来的接口，通常只是最顺手的版本，不一定是最好的版本。重要接口值得从几个不同方向各设计一版，例如：

- 把接口压到最小，让每个入口的杠杆最大。
- 为常见调用方优化，让默认路径最省心。
- 保留必要灵活性，但不把罕见分支暴露给所有调用方。

然后按深度、改动是否集中、接缝位置是否真实来比。选接口，不是选第一个能写出来的方案，而是选最能降低长期认知负荷的方案。

## 应用场景

- **业务形状变了（新规则轴、旧 if-else/大函数装不下）**：先抽到正确归属再改行为；用深度判断新接口与接缝，不要在旧容器硬塞分支。
- **实现 feature 时发现需要抽取、合并或下沉模块**：用深度判断新接口长什么样，接缝该放在哪。
- **代码读着累、改一处牵动很多地方、或者难测**：优先怀疑模块太浅，或概念散落在多个位置。
- **设计新模块接口**：先定归属和名字，再压接口、厚实现。
不适用：

- **不是主动审计工具。** CodeStable 没有“专门扫一遍代码找问题”的默认步骤；架构改进长在具体变化里。用户**明确要求**审某段代码时，用下文 **Review 动作**，仍须有范围。
- **不规定技术栈，不写具体代码。** 这里只给判断模块深浅和接缝位置的尺子。
- **原则文件，不是流程。** Design / Do 实现时对照；Review 审已有改动时对照。

## Review 动作（用户点名才审）

**不是流程步骤。** 只有用户明确要求 review / 评审 / 看看这改动 / 审一下 PR 时才进入。实现、快改、关闭都**不**自动 Review。默认只出判断与建议，**不擅自改代码**；用户说“按 review 改”再切 Do / 快改。

**有范围才审。** 用户指定的 diff、分支、PR、文件/目录或“刚改的那批”。没有范围就问一句要审哪一块，**不做无边界全仓审计**。

**先对照意图与 `.cs/`，再挑结构。** 这批改动想解决什么？project/epic spec、目标 issue 是否说得通？怪写法是否已有记录取舍？（开工协议见 `SKILL.md`。）

**用本文件的词审，不另发明一套。** 重点：归属与命名；深度（是否纯穿透层）；接缝是否为想象中的扩展；边界（校验/错误/危险操作）；经济性（见 [economy](economy.md)）；可测性是否扎在可观察行为。辅以相关 [quality](quality.md) 约束，只提会改变正确性或失败代价的点，不机械过九项表。

**按严重度说话。** 先给结论（可合 / 有条件可合 / 建议先改再合），再列少数高信号问题；每条：现象、为何要紧、建议怎么改（可选）。风格小偏好往后放或省略。

### 步骤

1. 锁定范围；读相关代码与测试；扫本范围相关 `.cs/`。
2. 对照意图：是否越界、是否漏验证。
3. 过本文件尺子 + 需要时 economy 梯子。
4. 组织汇报（见下）。要落地修改 → 问是否改，或按其授权切 Do/快改。

### 产物与汇报

默认**无强制落盘**。用户要求痕迹时：写入目标 issue 一节，或极短 note；不要为 review 新建流程实体。

汇报结构：一句话结论 → 必须处理 → 建议处理 → 可选/观察（可省略）；每条尽量带位置与改法方向。

不适用：未要求时的默认步骤；无范围全仓挑刺；当 Design 用（写码前安排实现）；当 Complain 用（行为已偏离预期）。
